## C01. Foundation and product loop

Delta is a standalone SillyTavern extension built from `kohz87/npc_state`, commit `a12b2937b5c1305e3e3017218a626478a5bedcdc`, directory `legacy/v0.2.x`, manifest version `0.2.23`. The seed includes the retained 0.2.18 engine and later hardening/enhancements actually present in that snapshot. Do not substitute another 0.2.x revision based only on its name.

The essential loop is: completed story exchange -> legacy-style dedicated scan -> grounded dossier update -> owned persistence/checkpoint -> relevant accepted continuity in the next roleplay request. Use legacy as the main implementation and behavior base, with selected Beta/Alpha features adapted into it. The nine phases are work stages, not nine runtime components or alternate operation modes.

No mandatory machine trailer in roleplay output, no separate mandatory Immediate/Development architecture, and no independent background dossier database. No dependence on installed legacy/Beta/Alpha extensions or their settings/data. Delta does not add an always-on server worker.

Maintain one canonical per-chat dossier state, one settings source, one persistence/checkpoint path and one relationship mechanics implementation. UI projections are reads of that state, not additional authorities.

Use the `npc_state_delta` installation/settings identity, `NPCStateDelta` public global and Delta-specific DOM, prompt, sidecar, recovery, writer-lock and bundle identifiers. Do not automatically discover or migrate another generation's data. Internal historical-shape readers retained in the seed are not a product promise of generational import support.

Application versioning is one synchronized release concern, separate from persisted schema/version families. The current application version is recorded authoritatively in `manifest.json` (`version`), `package.json` (`version`), `runtime-modules.json` (`applicationVersion`), `core.js` (`NPC_STATE_VERSION`), and the `bootstrap.js` version banner. Release-facing current-version derivatives are the README title/installable package name, the current release section in `DEVELOPMENT.md`, the top release entry in `CHANGELOG.md`, and current-version assertions in tests. Manual follow-up controls remain task-owned and lifecycle-stable: the global `Scan dossier now` action and the settings-level manual `Full scan current cast` action belong to Data & maintenance even when extension modules render out of order; optional automatic full-cast configuration belongs to Scanning, and the Diagnostics modal may expose its own manual `Full scan current cast` follow-up action only by delegating to the canonical `full-cast.js` owner. Portrait generation must not absorb unrelated maintenance/scanner actions. Every application release candidate must update all current markers together and validation must reject disagreement. Bundle, branch-lineage, diagnostics, storage, rollback-journal, and other persisted format versions remain independently governed and are never bumped merely because the application version changes. Historical review documents, migration fixtures, old-version regression names, and provenance records must retain the version they actually describe; never perform a global historical version replacement. Unreleased implementation work may remain on the current application version until release preparation is explicitly authorized, but it must not introduce a competing version marker.

Preserve the original repository GPL license and source provenance. Runtime must be self-contained. No GitHub/network source loading from reference projects.

## C03. Capture, scanner and routing — stage 3

Retain legacy's completed-message capture, latest-exchange routine scan, configurable scan cadence, manual Scan/Refresh, configured history modes, conditional focused relationship passes, malformed-response handling and necessary backfill behavior unless a task explicitly changes a path. Preserve source/branch ownership and late-result rejection. No Beta-style requirement that an owning scan must succeed before another ordinary generation may proceed.

Each valid assistant story receipt owns one deterministic turn/cadence increment at its actual raw-message boundary, independently of scanner success. Journal it before asynchronous scan dispatch; successful processing may safely consolidate at the same boundary. User/system/empty messages and duplicate receipt events do not increment turns. Failed, skipped, busy, canceled or delayed scans do not manufacture dossier updates, absence or lifecycle cleanup, nor transfer receipt changes to a later user boundary.

The seed's message handler awaits scanner work; retaining it is not a guarantee of nonblocking host behavior. Measure generation wait and provider contention separately. Do not introduce new waits or advertise foreground priority without verifying the actual selected host route.

Add a scanner connection-profile setting. An empty/default selection uses the existing host route. A selected route applies consistently to retained NPC model requests: automatic/manual scan, targeted Refresh, focused passes, repair/retry and applicable backfill. Ordinary roleplay keeps its configured route. Portrait generation remains its own host image workflow.

A missing/unavailable selected profile produces a clear recoverable error; never silently route to a different provider/model. Prefer request-scoped routing. Any temporary host setting changes must restore reliably and cannot redirect concurrent roleplay. One shared dispatcher should account for actual request counts, timeouts and cancellation. Do not add automatic completeness calls or additional passes solely to compensate for a larger contract.

Automatic post-scan repair is target-scoped. If the broad scan explicitly misses one existing NPC genuinely participating in current narrative exchange, Delta may queue that dossier for silent continuity repair. Structured World State, NPC Inner Chatter, roster/status blocks, or other evidence-only listings do not by themselves establish participation or authorize an established-dossier repair. Automatic repair queue entries are versioned, reason-scoped transient work owned by one source exchange; legacy/unversioned persisted entries are discarded on normalization, and `missed-participant` work must be revalidated against its owning exchange before dispatch. Automatic omitted-established-participant repair is bounded to at most one target per broad scan; multiple apparent omissions suppress that per-NPC fallback rather than becoming an implicit full-cast pass. A newly created or promoted dossier may receive its own targeted recent-history enrichment. New admission alone must never fan out targeted backfill requests across unrelated established active dossiers; the inherited v0.2.23 cast-wide topology sweep is intentionally retired. Manual Refresh/Scan and the separately opt-in current-cast scan remain explicit operations with their own scope.

## C04. Dossier establishment and evolution — stage 4

Retain identity/admission, aliases, role/species, actual/apparent age, durable Home Base / Usual Location, live state, personality, behavior profile, characteristic speech, mannerisms, background, memories, non-player ties and bounded profile-evidence evolution. Home Base is ongoing-life geography such as a home, workplace, headquarters, or regular haunt and is distinct from live Location; a temporary scene location cannot silently replace an established Home Base. Supported new facts can populate the first scan. Unknown fields stay unknown; do not infer merely because a field is blank. Omitted fields preserve accepted values.

Retain legacy refinement/evolution rules and the separation of durable identity, transient mood/condition, player-specific dynamics, and profile evidence. Do not silently replace its heuristics with Beta/Alpha's evidence contract during cleanup. Explicit later changes require a recorded behavior decision and tests.

Behavioral Profile is a bounded current set of target-general behavioral levers that translate durable identity into response/decision tendencies. Observed actions are evidence for those levers, not an action-history format. Labels are a soft semantic taxonomy, never mandatory slots: compatible names may consolidate into families such as Disposition, Cruelty/Mercy, Independence/Agency, Care/Warmth, Expressiveness, Conflict/Assertiveness, Threat Sensitivity, Analytical Style, and Social Presentation, while unknown supported labels remain allowed. Temporary anxiety or stress remains live Mood/Status unless established as a durable cross-context tendency; player-specific behavior remains relationship continuity; verbal production belongs Speech and recurring physical habits belong Mannerisms. Do not create empty/default Behavioral Profile categories merely to fill the taxonomy.

Durable profile summaries are CURRENT state, not history containers. When the scanner explicitly supplies an accepted `refine`, its full Personality, Speech or Appearance field and full bounded Mannerisms/Behavioral Profile list are authoritative after the existing safety/admission gates pass; omitted superseded clauses/rules retire instead of being appended back. Missing/`keep` lifecycle markers do not inherit that destructive full-summary authority: compatibility recovery may add grounded detail only when it preserves every established durable concept and also passes the field's normal safety gate. Personality morality conflicts and Speech evolution language remain disallowed on this path; lexical repetition inside negation such as `no longer` is not preservation of established meaning. Profile evidence, memories and their existing history owners retain longitudinal support separately. Unsafe full Behavioral Profile refinement rejects atomically and preserves the established profile. Protected agency/morality direction is evaluated across the whole proposal without collapsing mixed positive/negative evidence to neutral, including reversals hidden behind renamed categories and bounded negation such as `not independent`; ordinary cooperation or contextual mention of authority alone is not obedience. The same explicit-refine rule applies per appearance slot: accepted overall/named-form refinement replaces that slot's current summary while unrelated named forms remain preserved; unmarked/`keep` form updates cannot retire omitted established detail. Delta 1.0.28 additionally requires newly introduced durable meaning in runtime `refine`/recovery paths to be grounded in the supplied field evidence/story source rather than authorized by overlap with established wording alone; directly grounded clarification may still apply on first observation without being forced through gradual-development readiness. Mannerism and Behavioral Profile collection order is presentation-only, so reorder alone is not semantic change and cannot consume evidence. Evidence resolution is claim-body based, including polarity, and a matching concept label alone never proves that an observation is already represented. Delta 1.0.29 makes that admission claim-complete and target-NPC-specific, applies it consistently to flat Appearance reconciliation, evaluates evidence representation directionally, scopes negation/polarity to the relevant claim unit, requires explicit per-member proof before already-resolved bonds inherit collective semantics, and preserves copular/visibility/negation grammar when Shared appearance prefixes are deduplicated. Delta 1.0.35 permits one additional non-destructive recovery for established Behavioral Profile: a missing/`keep` state may admit only additive target-general rules when the returned full candidate preserves every established rule verbatim, every new rule is grounded by Behavioral Profile evidence, and the existing agency/morality conflict guards pass; omission never retires or rewrites established rules. Scanner and targeted Refresh extraction may place the same scene into multiple durable-field evidence arrays when it independently supports each field, including Speech and Behavioral Profile. Manual locks remain authoritative. User-authorized profile evolution also distinguishes narrative provenance: declarative user-authored canon may authorize grounded explicit or elapsed batch development immediately, while assistant/main-speaker prose remains observational evidence even when it describes itself as permanent. Questions, speculation, requests, conditionals, future wishes, and fully quoted user dialogue do not receive declarative canon authority. Ordinary additive Speech development may converge after two independent provenance-separated observations when each independently supports the same newly introduced claim in the full candidate; Speech replacement/reversal and Personality evolution retain the three-observation threshold. This candidate-centric gate is acceptance-time logic only and does not create a second persisted trait/voice store. Speech extraction and roleplay injection should favor observable voice production such as sentence shape, vocabulary, formality, directness, hedging, cadence, explanation/question style, and recurring verbal habits over generic adjectives.

Important Bonds / Key Relationships are compact non-player social continuity backed by one hidden graph. Canonical bond rendering is idempotent: repeated reconciliation must not append or multiply existing relation/dynamic fragments, including historical extra structural pipes, spaced-slash fragments, or truncation debris. Canonical stored bonds use one 360-character ceiling with a 260-character dynamic budget. Structured subject/relation/dynamic must be parsed before limiting; whole deduplicated dynamic fragments are admitted only while they fit, an over-budget trailing fragment is dropped intact, and a single unavoidable oversized fragment may be shortened only at a sentence, clause, or word boundary with no severed word or dangling structural separator. Scanner-edge normalization, social-graph storage/projection, ordinary dossier normalization, and manually locked bonds use the same canonical representation; smaller prompt/injection projections remain independent presentation budgets. A manual rewrite is authoritative for the edited direction. A manual deletion of a resolved counterpart bond removes the shared graph pair and mirrored structured projection in the same transaction so reconciliation cannot immediately recreate it from the counterpart; genuinely new later story/scanner evidence may establish a new bond normally. Corrupted legacy entries must still be removable when their structured subject prefix uniquely identifies the counterpart. When stronger evidence confirms an inferred social edge, confidence/provenance promotion must also reconcile its `inferred` status, including duplicate and reversed-edge normalization. Graph-capacity pressure ranks canonical confidence and may discard only strictly weaker continuity; an incoming inferred/migration/explicit edge cannot evict an equal- or higher-authority explicit/manual edge solely because the bounded graph is full.

Adopt overall appearance plus named appearance forms and current-form selection. Historical flat `appearance` is a compatibility input and resolved current-visible projection, not an independent canonical/manual appearance authority. Pre-form records may seed one safe Base presentation without fabricated alternate anatomy; new manual edits use the dedicated shared/named/current-form editor only. Define one resolver for dossier display, scanner comparison, portrait prompts and roleplay injection. The selected form's accepted anatomy, current outfit/condition and overall description must agree. A form switch does not erase another form's description. An observed undefined form preserves supported current presentation in a separate unnamed-current slot without inventing a form ID, duplicating form-independent details, or forcing the previous anatomy. Omission does not delete forms. Correcting one named form affects only that form unless the source explicitly supports a broader change.

The user-authorized birthday amendment is Delta-local deterministic metadata, not a donor engine: an ordered month table is required for a custom calendar; era and a complete manual fallback year/month/day are optional. Generate only stable calendar month/day values and label them generated. Grounded story facts and explicit manual Edit Dossier corrections may establish/correct dates. Manual birthday corrections are validated against the active calendar and use the same canonical birthday continuity engine without a model call; exact actual age and a compatible full owned date may derive a provisional birth year. When grounded calendar arithmetic proves that an existing dossier has reached its birthday, chronological age may advance deterministically. A compact numeric apparent-age estimate may follow the same proven integer delta only to preserve its already-established chronological/apparent offset; apparent age never supplies chronology, and manual Apparent age locks or provider-explicit visual evolution remain authoritative. For an existing yearless month/day birthday, an exact matching current date plus explicit owned birthday/nameday narration may perform one compatibility rollover and reanchor the derived year so repeated scans on that day are idempotent; a birthday first established in that same scan cannot assume the stored age is pre-birthday, and a provider-explicit chronological correction is not second-guessed by this compatibility rollover. Species and lifespan never supply chronology. Raw supported World State headers are passed to local calendar arithmetic separately from model context. Unknown/incompatible dates do not fabricate chronology; manual age locks, terminal death and owned rollback remain authoritative. An older manual fallback cannot roll accepted age backwards. See `docs/birthday-continuity.md`.

## C05. Terminal automatic death — stage 4

Retain grounded legacy lifecycle detection but remove automatic narrative reactivation/resurrection. Once confirmed dead, later model/structured/Refresh output cannot make the NPC alive or currently active again. Preserve historical identity, dossiers, memories, relationships and portrait references. Death does not delete the record.

An explicit user correction can repair an erroneous death. Delta may use the retained manual Restore control for that correction as long as it records correction provenance and does not infer current presence; it is not narrative resurrection. Owned-history rollback can remove a death whose source was deleted, edited or abandoned by a swipe. These are corrections of invalid state, not a narrative revival feature. They must not revive unrelated dead NPCs or bypass provenance. All automatic writers obey the same terminal rule.

Automatic stale lifecycle uses assistant-turn inactivity: defaults archive at 30 and delete at 50 since the later of lastSeenTurn and lastWorldActiveTurn. It runs only after a successful eligible scan with auto-pruning enabled (including the existing capacity-gated path), never merely on message receipt or scan failure. Present, world-active, retention-protected and scan/transcript-referenced NPCs are exempt. Only stale automatic archives participate in timed deletion; manual and death archives remain protected. A living unarchived dossier already beyond 50 turns may be removed directly with structured social/reference/pending-work cleanup. Explicit terminal death is protected independently of archive status, including when automatic death archiving is disabled: retain the dossier, history and references until explicit user removal or owned rollback invalidates the narrative record. Reuse the shared terminal policy.

## C06. Relationship scoring — stage 5

Retain the exact pinned legacy mechanics and interpretation as the initial Delta policy. Four independent NPC-to-player axes: Trust, Affection, Desire, Tension; default baseline zero; integer range -100..100 with separate signed fractional progress.

| Impact | Default maximum raw magnitude per axis | Maximum axes |
| --- | ---: | ---: |
| none | 0 | 0 |
| ordinary | 1 | 1 |
| meaningful | 2 | 2 |
| major | 5 | 3 |
| extreme | 10 | 4 |

For outward movement, multiply raw capped evidence by the legacy magnitude bands: `<30:1`, `<50:0.75`, `<70:0.5`, `<85:0.35`, `<95:0.2`, otherwise `0.1`. Movement toward neutral retains legacy's impact-sensitive resistance; extreme contrary evidence acts at full raw strength. Accumulate fractions before converting to whole displayed movement. Do not round away progress or reweight the model's proposal twice.

Gates are per axis and direction at 25/50/75/90, requiring meaningful/major/extreme/extreme respectively and stock minimum raw magnitudes 1/3/5/8. Retain legacy's configured-cap adjustment to gate minima. Reaching a locked boundary does not bank outward fractional progress; a qualifying event can unlock it even without an immediate visible point. Existing unlocked milestones, progress and reasons survive ordinary persistence and valid recovery.

Retain legacy overflow selection, including rejection of an ambiguous equal-weight tied group; retain its evidence and duplicate handling at baseline. Beta's priority tie handling/source-event duplicate refinements are optional discussion items, not approved changes. Do not substitute Beta's resistance curve or Alpha's default +/-1000 score scale, zero inertia, descriptive milestones, or absence of legacy event caps.

Score genuinely new directional evidence, never repeated narration of the same event. Desire needs its own grounded support; warmth, rescue and trust alone do not establish it. A zero numeric change may still update an appropriately grounded relationship description. Identity, agency, boundaries and other bonds dominate player relationship expression. Manual corrections and owned rollback must preserve the intended per-axis state; historical scans cannot replay old score events as new ones.

## C08. Persistence, history and removal of OOC commands — stage 7

Retain legacy sidecar storage, owner-qualified chat keys, lineage/swipe-aware snapshots, writer locking, revision conflicts, dirty-write retention/retry, recovery copies, deletion tombstones, rename/delete lifecycle handling and branch recovery. Full branch checkpoints remain byte-bounded recovery/swipe anchors. Delta 1.0.12 retains up to 8 MB of full checkpoints with a 2 MB ceiling per snapshot and independently versions a one-time legacy branch-history compaction. Compaction may retain only the current active lineage plus alternates still proven by SillyTavern's swipe state, and may drop unreachable sibling checkpoints/cards and rollback-journal chains not owned by the live head or a retained checkpoint. It must defer while destructive divergence remains unresolved, then retry after reconciliation; compaction cannot shorten the advertised active rollback-journal horizon. Delete/regenerate and message-edit events are linear replacement operations. Their destructive recovery target is exactly the surviving parent boundary at `divergence - 1`: restore it only from journal proof or an exact checkpoint, discard recovery artifacts owned by replaced descendants, and never substitute an older retained checkpoint or generic root for a missing parent. Near-tail replacements with at most one affected assistant exchange may rebuild from that exact parent and rescan the replacement; if multiple assistant descendants remain after a deep edit, preserve the current canonical dossier state and fail closed rather than rewinding later accepted continuity that cannot be deterministically replayed. Only explicit SillyTavern swipe events authorize sibling-branch retention. A known swipe may restore an exact sibling; an unseen swipe may use only its exact parent/root anchor and must then rebuild the new sibling. Destructive lineage identity is narrative-content based; mutable host `send_date`, generation ids and swipe indexes may assist host interaction but cannot by themselves authorize canonical rollback. The reversible journal owns chronological rollback and, in Delta 1.0.8, guarantees a contiguous 256 raw-message horizon from a trustworthy baseline using message position together with lineage identity. Recovery must distinguish same lineage, harmless forward extension, strict tail truncation and replacement divergence; a persisted lineage that is merely an exact prefix of the live chat cannot restore an older checkpoint. If no exact/proven target exists for a divergence, recovery fails closed by retaining the accepted canonical dossier and rebasing current ownership rather than walking backward to an older checkpoint/root. An explicit first-message swipe may still use its pre-message root anchor because the host has authoritatively declared alternate-branch semantics. Unchanged user/system boundaries must remain traversable even without undo mutations, and repeated same-message commits may coalesce only if their lineage ownership matches and referenced journal versions remain immutable. A retained descendant or a checkpoint other than the same boundary being replaced owns its sequence and required predecessors; coalescing must use copy-on-write when referenced, including fields returning to their original values and net-zero changes. Retained checkpoints keep their required predecessors within the proven message horizon; optional sibling retention cannot strand a retained chain. Journal rollback reverses structural state as well as fields: an NPC introduced only in deleted history disappears together with owned social references and pending work, while surviving NPC state returns to its prior narrative values. Social-graph undo should retain changed edges/slots rather than whole prior graphs where stable identities permit it. Existing user-owned metadata overlay/tombstone rules remain authoritative and cannot resurrect a narrative NPC whose existence was rolled away. Dirty local state that failed persistence cannot be silently replaced by an older sidecar after bounded-cache eviction; the persistence owner retains the newest accepted undurable snapshot until a later successful write or explicit authorized cancellation/removal. Hydration from any unsaved recovery source cannot establish durability. Every persistence failure exit, including transition from transient retries to permanent rejection, must preserve recoverable pending state or honor an explicit cancellation/retirement/ownership invalidation. Recovery cannot overwrite newer accepted in-flight mutations, bypass a remote revision conflict, or resurrect canceled data; bounded lifecycle transaction failures remain with their existing transaction recovery owner. The journal contains no transcript text and performs no model reconstruction. A numeric message position alone is not durable ownership; bytes may be diagnosed/limited for optional history but cannot silently invalidate an advertised active rollback horizon.

Remove narration-based OOC commands and command-only parser/listeners/exports/help/tests/backfill dependencies. Keep manual UI/API editing, add/remove/archive/restore as appropriate to terminal-death rules, locks, portrait handling and suppression safety. Trace shared dependencies so removing OOC does not remove ordinary scan or manually requested repair.

No automated operations on actual user databases during development. Import/recovery operates on its declared target and cannot cross an unproven history boundary or silently overwrite another chat.

A human current form cannot inherit wings, horns, tails, feathers, scales or other anatomy from a different form. Automatic prompt assembly is deterministic and subject-first: identity and accepted visible traits precede role, clothing, mood, location and composition, while global positive style is appended last. In Comma tags mode, explicit high-value visual anchors may be promoted into standalone tags only when directly grounded by accepted appearance prose. Appearance fragments already represented by those anchors may be omitted from tag output to avoid duplicate prose dilution, while unparsed appearance fragments must be retained. Explicit multicolor traits must preserve their stated components. Only explicit bounded contradictions, such as a stated hair color or an accepted "no wings/horns/tail" appearance clause, may add automatic negative tags; Delta does not infer absent traits from silence. Manual prompt edits cannot be silently overwritten by later UI refresh; only explicit rebuild may replace the working prompt. User-authored portrait prompt text must not be silently shortened by inconsistent UI/storage/builder limits. Global positive/negative style and per-NPC overrides use one shared 12,000-character safety budget per field, composition uses 6,000 characters, and final assembled prompts must preserve every accepted bounded component without a second lower truncation cap. SillyTavern/Image Generation provider limits remain external to Delta.

Every portrait operation is bound to its intended chat/NPC and revalidated after asynchronous work. Chat switches, NPC deletion, a closed/replaced workflow or a newer generation make an old completion stale. File-selection cancellation and failed generation/decoding leave the prior portrait unchanged. Once an explicit upload/application has been handed to the canonical mutation owner, the UI cannot pretend it is cancelable. A local mutation and a durable flush are separate states; failed persistence is reported as local-only and never advertised as saved.

Provide one clean, explicitly versioned native Delta import/export format, with no Alpha/Beta/legacy converters. The established Delta `NPCSTB01` / `npc_state_delta_bundle` version-1 codec remains the canonical format owner. Stage 8 may add declared manifest metadata for portable portrait settings and source-history audit. Validate the complete bundle and declared metadata before canonical mutation. Preserve supported dossiers, portrait binaries/references, relationships and signed fractions, milestones/reasons, appearance forms, terminal-death state and social state. Matching imports reconcile through the canonical importer; unrelated target dossiers are not silently deleted.

Source chat history cannot be replayed safely onto another target identity. Export may retain lineage/checkpoints/inline history for audit, but imported target history uses the target's existing safe baseline. Cross-chat import clears source message ownership fields rather than copying source identity or inventing target provenance. Activity counters are likewise chat-local chronology: matching target dossiers preserve their target-owned activity counters, while newly admitted foreign dossiers begin their inactivity clock at the target import turn; low or high source-chat counters are never compared directly to the target turn. Pending chronology-dependent development ledgers must likewise rebase onto the target safe baseline: accepted current characterization may survive, but source-chat message/turn observations cannot become target-chat evidence. This limitation must be disclosed in the import review and documentation. Failed validation performs no canonical mutation.

Import/export is accessible from the dossier UI and makes target/effects clear before application. Portable settings are limited to declared portrait-generation settings and are opt-in on import. Scanner profiles, credentials, storage pointers, scoring configuration and unrelated extension settings are not portable.

Diagnostics are compact, bounded and separate from ordinary dossier reading and canonical story/profile state. Delta 1.0.25 records an allowlisted per-chat operation ring automatically for scans and targeted Refresh; recording has no enable/disable setting. Diagnostic bundle version 3 keeps candidate equality (`candidateAlreadyRepresented`) separate from evidence coverage (`evidenceAlreadyRepresented`). Each retained NPC profile decision may include operation/source identifiers, field, old/candidate summary, provider/effective development state, bounded evidence IDs/concepts/samples, episode/NPC-binding state, aggregate readiness/fallback, locks, candidate/evidence resolution state, provider/effective reason source, candidate/reason grounding and final deterministic outcome. Birthday receipts are emitted only for NPCs with a relevant matched/supplied birthday, explicit age advance/correction path, or actual age delta; relevant rows may include bounded previous/current birth date, birth-year source, calendar age and reference date needed to explain hold/advance. A dossier Show/Hide control is presentation-only and cannot change recording, scanning, persistence, prompts, rollback, native transfer or Maintenance export. Data & Maintenance exports all retained records as a versioned compact JSON bundle and may clear only this runtime telemetry. Opening diagnostics must not initiate scans or expensive database processing. Preserve actual dispatcher aggregates/routes, focused/retry status, relationship signed fractions/gates, persistence status and clearly labelled local prompt estimates where exposed. Do not fabricate unavailable provider usage or a global pending-write metric. Never retain whole story transcripts, full private prompts, credentials or full provider responses in the operation store/export.

Stage 8 responsive dialogs keep close/cancel reachable with `dvh`/safe-area-aware bounded scrolling and touch-sized controls. Dossier selection, rail/document scroll, focus and unrelated editor contents remain owned by the existing dossier UI. Stage 8 refreshes affected components through that controller rather than rebuilding unchanged dossier content. See `docs/stage8-supporting-tools.md` for the implementation/verification boundary.
